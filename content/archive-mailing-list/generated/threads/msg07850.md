</div><ol class="mailing-list-replies"><li class="mailing-list-reply"><details id="msg07851" class="mailing-list-message"><summary><header class="mailing-list-message__header"><span class="mailing-list-message__author">Yousuf Fauzan</span><time datetime="2012-06-30T18:43:59-07:00">June 30, 2012 at 6:43 PM</time><span class="mailing-list-message__subject">Re: Large buckets with Secondary Index</span></header></summary><div class="mailing-list-message__content"><div class="mailing-list-message__body">I had a discussion with Tryn Mirell on Riak IRC. Here are a few things
discussed

1. LevelDB (till 1.1.x) suffers from compaction stalls
2. A benchmark to illustrate compaction stall (
<a href="http://cl.ly/2U3F1h3N2U3L461l000H">http://cl.ly/2U3F1h3N2U3L461l000H</a>)
3. Significant work being done in 1.2.x branch on (i) bloom filter support
for LevelDB (ii) handling LevelDB compactions
4. More detail on compaction stalls (
<a href="https://gist.github.com/fec80f5e1d4971eb506c">https://gist.github.com/fec80f5e1d4971eb506c</a>)
5. Artificially reducing write speeds will only delay the stall, not
prevent it.
6. Currently, you will initially see high throughput on LevelDB for a
single node, which will eventually drop to around 400 trans/sec.
7. Compaction does not happen on a per bucket basis as data is stored as
{bucket:key, value}. It occurs for the entire KV Store.

Last point above contradicted our initial assumption the compaction stall
is causing the performance degradation because if I pump data into a brand
new bucket then I get better write performance. However, the write speed
continues to be low on the older large bucket.

The way I store is, for each new date, I create a bucket A-&lt;date&gt; and store
the main data here as follows
(K1,V1), (K2, V2)....
Then in another bucket B, I add links for each of the above keys
So, K1 contains links for (A-&lt;old date1&gt;, K1), (A-&lt;old date2&gt;, K1), ...
(A-&lt;current date&gt;, K1)
As time passes, the size of links associated with each key in B increases.
However, it will stabilize to a certain number eventually (i.e. its not
gonna grow indefinitely)

The decrease in throughput occurs in the bucket B.

I think this decrease occurs because I am fetching K1 from B, adding a new
link, and then storing it.

Is there a way to append link to a key in a bucket without fetching it? If
not, is it possible to add such a feature?
