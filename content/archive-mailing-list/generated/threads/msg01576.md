The domain model is fairly simple. I have visitors, which get created for
any user who hits the site, visitors see alternatives (currently these are
ActiveRecord objects) and are tracked by creating experiences (the joining

Here is a simplified version of the model code:

class Riak::Visitor
  include Ripple::Document
  many :events,      :class_name =&gt; &quot;Riak::Event&quot;
end

class Riak::Event
  include Ripple::Document
end

class Riak::ShareEvent &lt; Riak::Event
  include Ripple::Document
end

class Riak::Experience
  include Ripple::Document
  one :visitor, :class_name =&gt; &quot;Riak::Visitor&quot;
  property :alternative_id, Integer, :presence =&gt; true
end

My problem is that I&#x27;d like to collect the set of visitors who have shared,
or more generally I&#x27;d like to return a set of visitors after narrowing down
the list by linking in specific kind of events. Well, my real problem is
that I still don&#x27;t quite grok MapReduce, but this is what I&#x27;m trying to
accomplish.

The riak-client code is included below (see visitors_who_shared). It returns
a list of all visitors found in the map phase where keep is true. This isn&#x27;t
surprising, but I&#x27;m not sure how to get the visitors if I don&#x27;t “keep” them
in that phase.

Thanks in advance for any help. I&#x27;m also happy RTFM and would appreciate
specific suggestions for doing nontrivial MR jobs in JavaScript.

class Riak::Alternative #not a riak doc
  attr_accessor :ar_id

  def initialize(ar_id)
    self.ar_id = ar_id
  end

  def visitors_who_shared
    Riak::MapReduce.new(Ripple.client).
            add(&quot;riak_experiences&quot;).
            map(map_filter_by_alternative).
            link(:bucket =&gt; &#x27;riak_visitors&#x27;, :keep =&gt; true).
            link(:bucket =&gt; &#x27;riak_events&#x27;).
            map(&quot;function(v){ return [[v.bucket, v.key]]; }&quot;).
            map(map_share_events).
            run
  end

  def map_share_events
    f = &lt;&lt;FUNCTION
function(v){
  var data = JSON.parse(v.values[0].data);
  if(data._type != &quot;Riak::ShareEvent&quot; ){
    return [];
  }else{
    return [[v.bucket, v.key]];
  }
}
FUNCTION
  end

  def map_filter_by_alternative
    f = &lt;&lt;FUNCTION
function(v){
  var data = JSON.parse(v.values[0].data);
  if(data.alternative_id !=  #{self.ar_id} ){
    return [];
  }else{
    return [[v.bucket, v.key]];
  }

FUNCTION
  end

</blockquote>The first concept you&#x27;ll have to give up with Riak is &quot;join tables&quot;, since you
can&#x27;t have indexes on them in the same way as you can with a relational DB.  A
more natural model would be to have a &quot;double&quot; of the ActiveRecord object,
which has the same key/id, and then links to all visitors who viewed that
alternative.  That is, you&#x27;d have another model (or maybe just an RObject,
depending on how you want to deal with it), like so:

class Riak::Alternative
  include Ripple::Document
  many :visitors, :class_name =&gt; &quot;Riak::Visitor&quot;
  property :alternative_id, Integer, :presence =&gt; true
  key_on :alternative_id
end

Then some portions of your MapReduce query will become simpler, some more
difficult.  I&#x27;m using a technique below I blogged about called &quot;forwarding&quot;,
which puts the data you want to return at the end of the query in the keyData
for subsequent phases.  In a relational DB you&#x27;d probably use a nested SELECT
or some crazy group by/having combination.  The Riak version feels more like a
fanout (and double-back).

########

def visitors_who_shared
  Riak::MapReduce.new(Ripple.client).
    add(&quot;riak_alternatives&quot;, ar_id.to_s).
    link(:bucket =&gt; &#x27;riak_visitors&#x27;).
    map(link_to_events_forward_visitor).
    map(map_share_events_to_visitor).
    reduce([&quot;riak_kv_mapreduce&quot;, &quot;reduce_set_union&quot;]).
    map(map_identity, :keep =&gt; true).
    run
end

# Inspect the links, select the ones that point to events, put the visitor&#x27;s
key as the keyData
# You could also put the whole object in the keyData, but this saves bandwidth
and computation.
def link_to_events_forward_visitor
&lt;&lt;-FUNCTION
function(object, keyData, arg){
    return object.values[0].metadata.Links.reduce(function(acc, link){
                                                      if(link[0] == &quot;events&quot;)
                                                          acc.push([link[0],
link[1], object.key]);
                                                      return acc;
                                                  },
                                                  []);
}
FUNCTION
end

# If the data is a ShareEvent, map to the visitor who created it
def map_share_event_to_visitor
&lt;&lt;-FUNCTION
function(v, keyData){
    var data = JSON.parse(v.values[0].data);
    if(data._type == &quot;Riak::ShareEvent&quot; ){
        return [[&quot;visitors&quot;, keyData]];
    } else {
        return [];
    }
}
FUNCTION
end

def map_identity
&lt;&lt;-FUNCTION
  function(v){ return [v]; }
FUNCTION
end

#########

The result of your visitors_who_shared method could then be used to vivify
Visitor objects (it&#x27;s straightforward, but I&#x27;m not putting the code here).

Long term, you&#x27;ll want to be creating your own Javascript built-in functions
instead of passing the source along with every query.    I&#x27;ve also only solved
one issue with your schema above (denormalizing the &quot;experiences&quot; into
&quot;alternatives&quot;).  Please ask again if you have other questions/issues.

You either take the hit at write time or at query time. Personally, I think
this is easier to understand and manage, but it may also depend on what other
queries you want to run.  For example, if your other queries are more focused
on the individual visitor, it might make sense to have a list of
alternative_ids in the Visitor class, instead of having something (experience
or alternative) link to it.  The key takeaway I&#x27;m trying to lead you to is that
data types that are effectively &quot;joins&quot; are less efficient/useful in Riak.
