notion of secondary indices. Not being bucket aware means bitcask has to
examine all bucket/key pairs to find the ones related to a given bucket. This
isn&#x27;t to say we won&#x27;t address the problem but merely to point out there&#x27;s some
engineering work required to solve the problem correctly.

innostore is moderately bucket-aware right now so I&#x27;ve forked it
(<a href="http://github.com/kevsmith/innostore">http://github.com/kevsmith/innostore</a>) and added bucket-aware key listing.
Based on some very basic testing I&#x27;m seeing 2.5x speed up in overall key
listing performance compared to the official version. I&#x27;m hoping the patch, or
a modified form of it, will make the next release. If you can handle inno being
a bit slower than bitcask and slightly more difficult to set up and tune then
this might be an option for you.

I&#x27;ve done some basic vetting of the code but I want to emphasize this is a
prototype only and hasn&#x27;t received anything even close to the normal amount of
testing we put into a release. Please keep this in mind if you decide to use my
forked repo.

</div></div></details></li><li class="mailing-list-reply"><details id="msg01551" class="mailing-list-message"><summary><header class="mailing-list-message__header"><span class="mailing-list-message__author">Kevin Smith</span><time datetime="2010-11-15T14:51:19-08:00">November 15, 2010 at 2:51 PM</time><span class="mailing-list-message__subject">Re: map-reduce Problem ?</span></header></summary><div class="mailing-list-message__content"><div class="mailing-list-message__body">In general, Riak backends combine the bucket name and key into a single value
used as the primary key. For the Basho-written backends the combined value is
an Erlang tuple of the form {BucketName, Key}.

When you list all the keys in a bucket, the backends execute a fold over all
their data. The function executed within the fold examines each tuple and keeps
tuples which include the desired bucket name. This arrangement means listing
keys is still not as scalable as it could be. Consider the case of a Riak
cluster storing two buckets, A and B. Bucket A has 5000 keys while bucket B has
250000 keys. Listing the keys for bucket A means examining 255000 (bucket A +
bucket B) to find the 5000 you really want.

The first round of listing keys improvements focused on reducing the memory
footprint of folding over the keys in each backend and aggregating their
results. Before the improvements we would manifest the aggregated list in
memory which didn&#x27;t scale for large datasets.

The next thing to improve, IMHO, is adding &quot;bucket awareness&quot; to each backend
and the vnode API such that Riak no longer has to examine each datum in order
to find the ones belonging to a specific bucket. This is what my patch to
Innostore does. Innostore is already &quot;bucket aware&quot; internally so I was able to
leverage this fact and constrain the scope of key access to only the desired
bucket.
