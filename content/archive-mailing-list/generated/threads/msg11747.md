<blockquote>How is the Scaling of Raik CS when setting up a few hundred servers in a
cluster?
</blockquote>
The upper limit of a cluster size depends on traffic load, hardware, and
network capacity, but anything approaching 100 servers is likely to run into
trouble due to inherent limitations in both Riak and the Erlang VM itself.  An
Erlang cluster is a full mesh, so the cluster overhead grows significantly with
the number of servers.

<blockquote>Does it make sense, to build a cluster of that size, or is it recommended to
have smaller pools of clusters and shard the Files over more than one cluster?
</blockquote>
Definitely should look at deploying multiple clusters.

<blockquote>What about stanchion as the potetial single point of failure, how to prevent
it from corupting the System? If I got it right, Stanchion handles the IDs of
Buckets and some user stuff. So if no further Buckets or users need to be
created, there is no need for stanchion at that time and up-/downloading can
go on as usual?
</blockquote>
You&#x27;re correct: user accounts and user buckets are the reason we need a
consensus system, and thus the reason Stanchion exists. For existing
users/buckets, as you indicate, files can be transferred without any
involvement from Stanchion.

It is possible to cluster Stanchion using traditional cluster tools.

(Why Amazon chose to use a global namespace for buckets is a mystery beyond my
ken.)

<blockquote>As I want to use riak cs for large files (50MB-15GB) is it possible to raise
the chunk size up to these Filesizes, to prevent the system from heavy
network traffic?
</blockquote>
Definitely not. Erlang&#x27;s distribution protocol will behave badly with objects
that large.

</div><ol class="mailing-list-replies"><li class="mailing-list-reply"><details id="msg11797" class="mailing-list-message"><summary><header class="mailing-list-message__header"><span class="mailing-list-message__author">Andrew Stone</span><time datetime="2013-07-27T22:51:14-07:00">July 27, 2013 at 10:51 PM</time><span class="mailing-list-message__subject">Re: Scaling Riak CS to hundreds or thousands of servers</span></header></summary><div class="mailing-list-message__content"><div class="mailing-list-message__body">Hi Andre,

The blocks are going to be spread across some subset of that 100 servers.
Since Riak CS stores the chunks inside Riak they are hashed based on
primary key. Currently there is no way to co-locate chunks in Riak CS. You
can read more about How riak manages storage here:
<a href="http://docs.basho.com/riak/latest/theory/concepts/Clusters/let">http://docs.basho.com/riak/latest/theory/concepts/Clusters/let</a>

While it is possible to change the n_val (number of times an object is
replicated) on buckets inside Riak, it is not easy or advisable to do so
with Riak CS. Additionally, even if Riak CS allowed you to set the n_val
for individual CS buckets Riak itself does not support changing the n_nval.
Riak CS generates block keys and prefixes bucket names, and is generally in
charge of how it chunks and stores your data inside Riak.

-Andrew
