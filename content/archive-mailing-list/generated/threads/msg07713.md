users.  They have a limited length and both the user data and the
links have to be saved at the same time.

What you can do is emulate a set using a separate bucket and secondary indexes.

So basically the bucket would look like this:

So if I&#x27;m a friend of yours,

PUT /buckets/friends/keys/eric-morgan
x-riak-index-friend_id_bin: morgan
x-riak-index-user_id_bin: eric
Content-Type: application/json

{&quot;user_id&quot;: &quot;eric&quot;, &quot;friend_id&quot;: &quot;morgan&quot;}

Then you can fetch a set of my friends by doing a 2i query for the
bucket friends and the index
user_id.

If you want to a set of all the people that have friended you, do a 2i
query on friend_id with the value &quot;morgan&quot;.

You can quickly see if we&#x27;re mutual friends by fetching:

/buckets/friends/keys/eric-morgan and /buckets/friends/keys/morgan-eric.

If both are found, then we&#x27;re mutual friends.

Eric.

Hi, Morgan.

<blockquote>1 - Are Link walking in Erlang fast &amp; easy ?
</blockquote>
Link-walking in the Erlang client is provided via the MapReduce
interface. Instead of a &#x27;map&#x27; or &#x27;reduce&#x27; phase, specify a &#x27;link&#x27;
phase like:

    {link, Bucket, Tag, Keep}

Bucket is either a binary name of a bucket to match, or the atom &#x27;_&#x27;,
which matches any bucket. Tag is either a binary tag to match, or the
atom &#x27;_&#x27;, which matches any tag. Keep is a boolean with the same
meaning as in map and reduce phases.

<a href="http://wiki.basho.com/MapReduce.html#Erlang-Query-Syntax">http://wiki.basho.com/MapReduce.html#Erlang-Query-Syntax</a>

<blockquote>2 - Is it possible to check fast if A -&gt; B -&gt; A (still in Erlang)? (&#x27;-&gt;&#x27;
represents Links)
</blockquote>
The fastest way to do this is to fetch both A and B and look through
the links they contain.

HTH,
Bryan

<blockquote>Why would you think that fetch both user and look through the links is
fastest than A -&gt; B -&gt; A ? Are links really that slow ?
</blockquote>
It&#x27;s not that links are that slow, but that they&#x27;re not that focused.
Unless you&#x27;re using B&#x27;s key as the tag on the link from A, and A&#x27;s key
as the tag on the link from B, you&#x27;ll have to follow all &quot;person&quot; or
&quot;friend&quot; (or whatever) links from A, and the same from B.  So, what
you&#x27;d actually be walking is A -&gt; [any person/friend] -&gt; A.  You could
put a map or reduce phase between the two link phases to filter out
everything but B, but my bet is that simply fetching A and B
individually will be much faster than setting up and tearing down the
MR framework.

YMMV, always benchmark real data, etc.

-Bryan
