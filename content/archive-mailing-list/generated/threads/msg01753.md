changing the &#x27;n_val&#x27; from 3 to 1 and also the backend from bitcask to ets, and

It&#x27;s expected that, especially when running basho_bench, your cluster will not
use that much CPU. Riak is mostly I/O-bound, which is a good thing (vs. wasting
CPU not delivering data to you).  I would definitely expect network and disk
(and possibly RAM) to be the primary limiting factors.

</blockquote></div><ol class="mailing-list-replies"><li class="mailing-list-reply"><details id="msg01761" class="mailing-list-message"><summary><header class="mailing-list-message__header"><span class="mailing-list-message__author">Sean Cribbs</span><time datetime="2010-12-09T06:04:52-08:00">December 9, 2010 at 6:04 AM</time><span class="mailing-list-message__subject">Re: Ring Cluster and CPU idle time</span></header></summary><div class="mailing-list-message__content"><div class="mailing-list-message__body">If you&#x27;re using ETS, then yes that makes sense that the majority of the time
would be CPU (there&#x27;s no disk to wait on!).  One thing - when you say 60% of
available CPU, is that 60% of one core, or 60% of 12 cores (sometimes reported
as 720%)? The latter seems highly unlikely.

There are some generic things you can do to tweak Erlang and Riak for multicore
computers, many of them referenced on this page:
<a href="http://erlang.org/doc/man/erl.html">http://erlang.org/doc/man/erl.html</a> Of special note are:

+A - how many OS threads will be in the async thread pool (handles IO, some
system calls)
+S - the number of scheduler threads to create (usually 1 thread per CPU)
+sct - specify the CPU topology (useful for NUMA processors like Nehalem)
