<blockquote>Those limitations leaves us a single option of Riak Search and I have a

</blockquote>I&#x27;m working on a new solution, named Yokozuna, that integrates Riak and

<a href="https://github.com/rzezeski/yokozuna">https://github.com/rzezeski/yokozuna</a>

<blockquote>1) We saw, that after enabling search option and adding search precommit
hook, store speed (our tests were
done on single test node) became x10 slower. Is it normal?

</blockquote>Degradation of throughput after enabling Riak Search is normal.  Riak
Search does a lot of work during index time.  It has to analyze the data
and each indexed document has a good chance of causing writes to every node
in the cluster because of term-based partitioning.

<blockquote>2) If we have dedicated node in cluster for search (which would not be
used for KV store/get operations) would
it do some impact of general cluster performance?

</blockquote>You cannot dedicate a node for Riak Search.  Every node is required to
participate in KV.  Every node must have Riak Search enabled for search to
work.

<blockquote>3) For 1M keys in cluster search runs very fast. How it would scale for
100M (or even much more keys)?
How it would scale with number of nodes in cluster?

</blockquote>This depends on the query.  A single-term query with a reasonable result
set typically has a latency of a disk seek plus a few milliseconds.  This
is the benefit of term-based partitioning, at query time.  A boolean query
containing one large result set, even if the others are small, can bite you
because of sub-optimal logic in the intersection code.  A range query can
produce latency variance because it requires connecting to a covering set
of vnodes.

Scaling out will not lower the absolute latency for single-term queries,
since it queries one node, but it can potentially reduce concurrent query
contention thus reducing latency variance and improving throughput.

Scaling out may hurt range queries as it will require more nodes to
participate in coverage.  TCP incast could become an issue with enough load.

<blockquote>
1) Is search enabling has any impact on read latency/throughput?

</blockquote>If you are reading and searching at the same time there is a good chance it
will.  It will cause more disk seeks.

<blockquote>2) Is search enabling has any impact on RAM usage?

</blockquote>Yes, the index engine behind Riak Search makes heavy usage of Erlang ETS
tables.  Each partition has an in-memory buffer as well as an in-memory
offset table for every segment.  It also uses a temporary ETS table for
every write to store posting data.  The ETS system limit can even become an
issue in overload scenarios.

<blockquote>3) In production we have no search enabled. What is the best way to
enable search without stop production? I thought about something like:
1) Enable search node after node.

</blockquote>You could change the app env dynamically but that&#x27;s only half the problem.
 The other half is then starting the Riak Search application.  I think
application:start(merge_index) followed by application:start(riak_search)
should work but I&#x27;m not 100% sure and this has not been tested.  You&#x27;ll
also want to make sure to edit all app.configs so that it is persistent.

    2) Execute some night script that runs on all keys and overwrite them
<blockquote>back
with proper mime type.

</blockquote>Yes, you&#x27;ll want to install the commit hook on the buckets you wish to
index.  Then you&#x27;ll want to do a streaming list-keys or bucket map-reduce
and re-write the data.

4) If we see that search overhead is something we can&#x27;t handle, is there
<blockquote>simple
way to disable it without stop production?

</blockquote>I think the best course of action in this case would be to disable the
commit hook.  But you would have to keep track of anything written during
this time and re-write it after re-installing the hook.  If you don&#x27;t then
you&#x27;ll have to re-index everything because you don&#x27;t know what you missed.

5) In what case we would need repair? It is said - on replica loss, but if
<blockquote>I understand
correct we have 3 replicas on different nodes don&#x27;t we? If it happens
how difficult and
long would it be for large cluster (about 100 nodes)?

</blockquote>Repair is on a per partition basis.  Number of nodes doesn&#x27;t come into
play.  Repair is very specific in that it requires the adjacent partitions
to be in a good, convergent state.  If they aren&#x27;t then repair isn&#x27;t much
help.

A lot of these entropy issues go away in Yokozuna.  Repairing indexes is
done automatically, in the background, in an efficient manner.  There is no
need to re-write data or run manual repair commands.

</div></div></details></li><li class="mailing-list-reply"><details id="msg08936" class="mailing-list-message"><summary><header class="mailing-list-message__header"><span class="mailing-list-message__author">Gordon Tillman</span><time datetime="2012-10-16T07:56:08-07:00">October 16, 2012 at 7:56 AM</time><span class="mailing-list-message__subject">Re: Riak Search</span></header></summary><div class="mailing-list-message__content"><div class="mailing-list-message__body">Pavel as an alternative to re-writing the objects to cause them to be indexed,
you may invoke what I call a map operation with side-effects.

You define an Erlang map-phase function as follows:

map_reindex({error,notfound}, _, _) -&gt;
    [];
map_reindex(RiakObject, _, _) -&gt;
    riak_search_kv_hook:precommit(RiakObject),
    [].

You want to run that against all of the keys in the bucket by posting a mapred
job like this:

{
    &quot;inputs&quot;: &quot;&lt;your-bucket&gt;&quot;,
    &quot;query&quot;: [
        {
            &quot;map&quot;: {
                &quot;function&quot;: &quot;map_reindex&quot;,
                &quot;language&quot;: &quot;erlang&quot;,
                &quot;module&quot;: &quot;&lt;your-module&gt;&quot;
            }
        }
    ],
    &quot;timeout&quot;: &lt;your-timeout&gt;
}

We have used this technique to re-index rather large clusters and it runs
quickly because you are doing it in parallel across all of the nodes in the
cluster.
