</blockquote>Hi Sujay,

The latest release in the 2.0 series is 2.0.6 [0]. Please use this version
if you upgrade to 2.0.

Please also review the documentation about the new &#x27;riak.conf&#x27;
configuration file [1][2]. 2.x installations should use the new format, but
you can continue to use the &#x27;app.config&#x27; format from Riak 1.x. To maintain
complete backwards compatibility when using &#x27;app.config&#x27;, please add

[{default_bucket_props,
  [{allow_mult,false}, %% have Riak resolve conflicts and do not return siblings
  {dvv_enabled,false}]}, %% use vector clocks for conflict resolution
  %% other settings
]

to &#x27;app.config&#x27;. This will ensure that your existing application continues
to work exactly as before. When using &#x27;riak.conf&#x27;, these settings will be
applied automatically.

</div><ol class="mailing-list-replies"><li class="mailing-list-reply"><details id="msg16371" class="mailing-list-message"><summary><header class="mailing-list-message__header"><span class="mailing-list-message__author">Dmitri Zagidulin</span><time datetime="2015-08-06T06:13:15-07:00">August 6, 2015 at 6:13 AM</time><span class="mailing-list-message__subject">Re: Rolling upgrade from 1.4.2 to 2.0.5</span></header></summary><div class="mailing-list-message__content"><div class="mailing-list-message__body">Sujay,

You&#x27;re right - the best way to verify the backup is to bring up a separate
5 node cluster, and restore it from the backup files.
The procedure is slightly more involved than untar-ing, though. The backed
up ring directories from the original cluster will contain the node ids
(which rely on their IP addresses, etc). Since the new re-hydrated cluster
is likely to have different IPs from the original one, there&#x27;s a few more
steps you need to take.

The procedure of standing up a new cluster from backups is outlined here:
<a href="http://docs.basho.com/riak/latest/ops/running/nodes/renaming/#Clusters-from-Backups">http://docs.basho.com/riak/latest/ops/running/nodes/renaming/#Clusters-from-Backups</a>

There is one other important step to remember. If, by any chance, you&#x27;re
bringing up the new cluster on the same network as the old cluster is
running on, be sure to modify the Erlang cookie in the new cluster (so that
as far as Erlang is concerned, they&#x27;re existing on different networks).
The Erlang cookie must be modified in /etc/riak/riak.conf so the new
cluster does not conflict with any existing cluster.

Let us know if you have any further questions.

Dmitri

you&#x27;re bringing up the new cluster on the same network as the old
cluster
is running on, be sure to modify the Erlang cookie in the new
cluster (so
that as far as Erlang is concerned, they&#x27;re existing on different
networks).
The Erlang cookie must be modified in /etc/riak/riak.conf so the
new cluster does not conflict with any existing cluster.
