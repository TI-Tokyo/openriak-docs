<blockquote>More posts/ talks on actual use cases, agreed. The funny thing is that
riak is actually one of the dead simplest nosql systems out there. There
really isn&#x27;t much you need to know to use it or set it up.

</blockquote>I disagree. Yes, Riak is in general a simple system from an architecture
standpoint.  But often the that simplicity is an obstacle, as you must
solve more complex problem using Riak as a base.

E.g.

What are good strategies and data structures amenable
to sibling resolution?
How to trade off between secondary indexes and search?
How to configure search indexes so it does not blow up when you got very
high volume low cardinality or very high cardinality terms (faking
multicolumn indexes and bucketing)?
How to transition data in the store between formats?
How to reindex data in the store?
How to repair data in the store if you loose a node without the Enterprise
version?
What is the tradeoff between storing different data times in the same
cluster or multiple clusters?

These are all complex issues that Riak&#x27;s clean by simple architecture
leaves up to the user to figure out.

</blockquote>I agree, distributed systems are hard, even when they are simple.

<blockquote>How to trade off between secondary indexes and search?

</blockquote>This is an area I am actively working on, it just isn&#x27;t too visible to the
outside world yet.  I&#x27;ve recently started a prototype to fuse the 2i
interface on top of Search&#x27;s engine.

<blockquote>How to configure search indexes so it does not blow up when you got very
high volume low cardinality or very high cardinality terms (faking
multicolumn indexes and bucketing)?

</blockquote>I&#x27;m also doing work on this to make conjunction queries safer, do less
work, and have better latencies.  A query that produces a &quot;large&quot; result
set is still problematic but a conjunction of small and large result sets
will be much, much better.  I saw very significant improvement on a
particular work load but I need to do more benchmarking on &quot;real&quot; hardware.

<a href="https://github.com/rzezeski/riak_search/tree/rz-conjunction">https://github.com/rzezeski/riak_search/tree/rz-conjunction</a>
<a href="https://github.com/rzezeski/riak_search/tree/rz-no-unnecessary-work">https://github.com/rzezeski/riak_search/tree/rz-no-unnecessary-work</a>

<blockquote>How to reindex data in the store?
How to repair data in the store if you loose a node without the Enterprise

</blockquote>These are two HUGE pain points in Search.  Currently it is my #1 problem to
address and it will be a multi-faceted approach.  The first thing I&#x27;m doing
is building a repair cmd which will allow you to specify a broken partition
and it will smartly rebuild it based on the surrounding partitions.  I&#x27;ve
already done a prototype that passes some basic tests but it has diverged
into some riak_core work to help support it.  These are the prototype
branches:

<a href="https://github.com/basho/riak_search/tree/rz-repair-cmd">https://github.com/basho/riak_search/tree/rz-repair-cmd</a>
